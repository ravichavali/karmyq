Other zod-4 changes that were checked and **do not** change behaviour for our inputs (4.4.3):
- `.email()`: the same verdict as zod 3 on `a@b.co`, `user+tag@…`, `a.b@sub…`, `o'brien@…`, `x@localhost` (reject) and `é@…` (reject).
- `.datetime()`: the same verdict on `Z`, fractional `Z`, `+02:00` offset (reject in both) and no-seconds (reject in both).

- A custom message string still reaches the issue: `z.string().uuid('Invalid UUID format')` and `z.guid('Invalid UUID format')` both yield `message: "Invalid UUID format"`.
- `ZodError.issues` exists and `.errors` is `undefined`. `validate.ts:38,86` already reads `issues || errors`.
- `ZodSchema` is a **type-only** alias of `ZodType` in zod 4 (`node_modules/zod/v4/classic/compat.d.ts:43`). `validate.ts:2` uses it only in type positions, so the import is elided.
- `.omit().extend().strict()` on an unrefined object still works (`socialGraphContextClient.ts:9-12`). No shared schema uses `.refine`, `.superRefine`, `.transform`, `z.record`, `errorMap`, `invalid_type_error` or `required_error`. The only `error.format()` is in a doc comment (`src/schemas/requests/index.ts:99`).
- `.strict()` and `.passthrough()` are deprecated in zod 4 but still behave as before. Renaming them is **not** in scope.

**Why `z.guid()` and not strict `.uuid()` + fixture rewrites** (a recommendation, for the maintainer to confirm at plan review):
1. Live ids are RFC-compliant. Tables default to `uuid_generate_v4()` / `gen_random_uuid()`, and the curated demo derives ids as v5 with the variant bits set (`services/simulation-service/src/fixtures/curatedDemo/compiler.ts:46-53`). So strict would not break the demo today.
2. However, **~130 test fixture ids are non-RFC**. They are spread across 18 service/root test files and `tests/fixtures/reputation-disclosure-inventory.json` (41 ids), plus `infrastructure/postgres/seed-e2e.sql` and `seed/create-simple-test-data.sql`. Under strict validation, those seeds make `/me/community-summary` and relationship-context answer **500** (a parse throw inside the handler), not 400.
3. These schemas exist to fix the **disclosure shape** (`.strict()` key sets, ADR-082), not to police UUID versions. Postgres's `uuid` type accepts any 8-4-4-4-12 hex, so the DB is the real arbiter of what an id is.
4. `z.guid()` keeps D6 a no-behaviour-change dependency PR. Tightening to RFC-only would be a separate decision, and could be captured in `docs/IDEAS.md` if wanted.

  import { readFileSync } from 'fs';
  import path from 'path';
  import type { ZodType } from 'zod';
  import { commonSchemas } from '../../../middleware/validate';
  // …the exported schemas from Step 1…

  const RFC_V4 = '75648739-6e64-4d8b-b594-0fd70f609d2d';

    '11111111-1111-1111-1111-11111111111',
    '11111111111111111111111111111111',
    '{11111111-1111-1111-1111-111111111111}',

    // …one per site; 15 total…
