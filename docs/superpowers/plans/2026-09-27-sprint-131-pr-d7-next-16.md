## What "local Playwright" can and cannot prove on this box

This is the Windows box (`uname -s` = `MINGW64_NT-*`): **no local Docker** (`docker: command not found`). The demo API's `ALLOWED_ORIGINS` is `https://karmyq.com` only (`infrastructure/docker/docker-compose.prod.yml:22` and siblings), so a locally served frontend cannot log in against the demo. Therefore:

| Proof | Where | Covers |
|---|---|---|
| The real frontend image builds | CI `Test Docker Build` (the job #246 failed) | M2 end to end, on Linux, in the real Dockerfile |
| The runner-stage layout boots | Local: rebuild the runner stage's exact COPY layout in the scratchpad, then `node server.js` | M2 and M5 for the frontend, plus the `headers()` contract |
| Frontend pages render and hydrate | Local Playwright over pages that need no API: `/login`, `/demo` (public, `apps/frontend/CONTEXT.md:125`), a 404 | M5, and the React runtime under 16 |
| Landing export renders and hydrates | Local Playwright over `apps/landing/out` served statically | M1, M4 and M5 for landing, including `/404` |
| Authenticated flows | **Post-deploy** Playwright on karmyq.com, read-only, one login | everything behind auth |
| The demo actually serves the new landing | Post-deploy: `karmyq.org/docs/` shows the merge sha | the silent-failure path in `scripts/deploy.sh:177-190` (below) |

⚠️ **`scripts/deploy.sh:169-190` builds landing ON the demo host, and a failed build only `log_warn`s.** The deploy still reports success, and the old site keeps being served. A green deploy is therefore **not** evidence that landing built under next 16 on ARM64. The docs layout renders `build.json`'s `commitSha` (`apps/landing/src/app/docs/layout.tsx:18`, written by `scripts/generate-docs.ts:641-656`). The smoke requires that sha to equal the merge commit's short sha.

## Review Focus

1. **The type-check scope is the program next 16 runs, not a string in tsconfig.** The scope test must build the **whole program**: `ts.createProgram(...).getSourceFiles()`, not the root names in `parseJsonConfigFileContent(...).fileNames`. `exclude` only filters roots, so a test file that a source file **imports** still enters the program and gets checked. (Plan review, 2026-09-27; a scratch probe confirmed it: an excluded `tests/helper.test.ts` imported by `src/a.ts` is absent from `fileNames`, present in `getSourceFiles()`, and reports TS2322.) The test must go red on each of these:
   - a re-included `tests/**` (M-a);
   - a test file the exclude doesn't cover, such as `src/**/*.test.ts` (M-b);
   - an excluded test file that source **imports** (M-d);
   - a tsconfig with configuration errors (M-e).
2. **Every runner-stage COPY source exists after a 16 build.** Line 80's failure shows that a Dockerfile can reference an output that has disappeared. Task 4 checks every `COPY --from=builder` source under `.next/` against a real build, not just line 80.
3. **Landing under Turbopack.** `transpilePackages: ['styled-jsx']` was a webpack workaround for a dual-React dispatcher error, and its comment (`apps/landing/next.config.js:5-9`) names `/404` and a Pages Router `/500`. **Evidence (plan review, 2026-09-27):** landing is App Router only (`apps/landing/src/app/`, no `src/pages/`), and the existing next 15 export in `apps/landing/out/` has `404.html` and **no `500.html`**. A static export has no server to render a 500. So the requirement is:
   - `/404` exports, and renders in a browser with **no** `Invalid hook call` or dispatcher error in the console.
   - The 16 export also has no `500.html`, asserted by Task 5 Step 4. If 16 *does* emit one, it gets the same browser check, and the finding is recorded.
   - The `next.config.js` comment's `/500` claim goes to `docs/IDEAS.md` for correction. This PR does not change that comment.
4. **The `@swc/helpers` override is still load-bearing.** After the splice, `require.resolve('@swc/helpers/_/_interop_require_default', {paths:[<next dir>]})` resolves to the 0.5.23 node, and `npm ls @swc/helpers` shows one version.
5. **Service suites #246's CI never reached.** Expected: every **runnable** Turbo task **executed** (not replayed from cache) and green, with no edits outside the file map.
   - **Derive the expected count; never hard-code it.** Get it from `npx turbo run test --dry-run=json`, counting tasks whose `command` is not `<NONEXISTENT>`. On 2026-09-27 that gave 27 runnable of 30 listed, **26 of them cache HITs**, which is why a plain `npm test` proves nothing here. The earlier "25" came from #246's CI summary (`25 total`), which is a different context.
   - Reconcile CI's own `Tasks: N total` against its log. Don't assume the two counts match.
