# Sprint 117: Controlled Demo Reset and Curated Fixtures — Design Spec

**Date**: 2026-07-02
**Status**: Approved
**Version**: v11.25.3 → v11.26.0
**Sprint Branch**: `agent/codex/sprint-117-curated-demo-reset`

---

## Overview

The guided Maria demo currently depends on additive rehearsal against a continuously mutated database.
That made story selection fragile: the simulator could consume the selected requests, historical data
could no longer satisfy the intended relationship shape, IDs had to be copied by hand, and the old
truncate script no longer covered the platform's current schemas. A visually successful demo could
therefore conceal invalid lifecycle, privacy, or age-dependent state.

Sprint 117 replaces that workflow with a controlled full demo-data reset and a compact, deterministic
fixture system derived from the platform's implemented contracts. A typed manifest defines a stable
historical baseline using semantic keys and ages relative to one reset anchor. A guarded orchestrator
pauses mutation, verifies the target, backs up the database, atomically rebuilds the baseline, creates
the two live Maria decisions through ordinary APIs, and makes outward privacy-scoped API validation the
authority for enabling the demo. Planned demo downtime is approved.

The baseline is intentionally curated rather than large. It provides enough people, communities,
topology, lifecycle states, and age bands to exercise the product without recreating the noisy and
uninspectable 500-user simulation. After validation, a separate ambient population may evolve under
the simulator; the protected narrative core never may. Fixture tuning after live observation is an
expected manifest edit, while privacy, lifecycle, and relationship floors remain hard invariants.

### Core Principle: Deterministic Inputs, Truthful Outputs

The manifest controls the story setup, but only ordinary privacy-scoped API behavior can declare the
demo ready.

## New Concepts

### Reset anchor

One UTC instant captured at the start of a reset. Every manifest age is an offset from this anchor
(`fresh_request = anchor - 2h`, `recent_exchange = anchor - 3d`, and so on). Re-running the reset
reproduces the same relative ages without freezing the platform at a calendar date.

### Semantic fixture key

A stable human-readable key such as `person.maria`, `community.portland-mutual-aid`, or
`exchange.maria-couch-history-1`. Historical UUIDs are deterministically derived from these keys.
Live request, match, and provider-offer IDs are generated by the application and accepted only after
authoritative readback.

### Protected core

Maria and every person or record required to preserve her narrative and its validation floors. All
protected people are synthetic and are excluded from simulator actor selection. Maria is an active
ordinary member in every membership; she never holds an admin or moderator role.

### Ambient population

Synthetic people and activity that are safe for the continuous simulator to mutate after validation.
Ambient changes may add texture but may not be required for any guided story or acceptance assertion.

### Temporal lanes

- **Durable history** uses repeated exchanges and sufficient stability to keep Maria's required
  topology valid for a long operational runway.
- **Aging examples** intentionally demonstrate fresh, fading, nearly-forgotten, retained, expired,
  and forgotten states and are expected to transition as real time passes.
- **Live stories** are open decisions with a finite request TTL. They rotate through ordinary APIs
  before their runway falls below the configured floor.

### Fixture health

A read-only verification result containing story coherence, API/privacy assertions, topology floors,
expiry runway, simulator exclusion, and a clear ready/not-ready state. Health checks never repair or
refresh data automatically.

### Projection rebuild

An application-owned deterministic replay from historical source fixtures into derived relationship
and reputation state. The manifest declares completed exchanges, feedback, and their ages; it does
not hand-author trust edges or scores. Rebuild code uses the same domain rules as live event handling
and preserves source event time, so age-dependent projections start truthful at the reset anchor.

## Reset Safety Boundary

The reset command is destructive only with an explicit `--apply` flag and all of these controls:

1. `--dry-run` is the default and reports the database fingerprint, classified tables, row counts,
   planned seed counts, anchor, and expected downtime steps.
2. The database must satisfy an explicit demo-environment fingerprint. Hostname alone is insufficient;
   production-like or unknown targets fail closed.
3. The command disables public demo entry, pauses the simulator and cleanup jobs, and acquires a
   PostgreSQL advisory lock before mutation.
4. A timestamped restorable backup is required before truncate. Backup failure aborts the reset.
5. Every table in the managed application schemas is classified as `reset`, `reseed`, or `preserve`.
   An unclassified table fails preflight so schema growth cannot silently escape cleanup.
6. Schema definitions, extensions, migration bookkeeping, and explicitly immutable catalogs are
   preserved. Mutable application data and configuration are reset; required global/community
   defaults are recreated from the manifest.
7. Truncate, historical source load, and deterministic projection rebuild are one database
   transaction. A seed/compiler/projector failure rolls it back. A later outward-validation failure
   keeps the demo disabled and provides backup restore or safe rerun instructions.
8. Cleanup resumes only after baseline and live-story validation. Simulation resumes last and only
   after the protected-core exclusion assertion passes.

The obsolete `scripts/truncate-database.*` path is fixed forward into the governed workflow; no
parallel `reset-v2` escape hatch remains.

## Fixture Coverage

The initial target is approximately 30–40 people across six communities. Counts are tunable manifest
parameters, but the behavioral matrix is not optional.

### People and roles

- Maria Reyes: dedicated public demo persona; synthetic, active, member-only, protected.
- Rich ordinary helper: protected and selected to satisfy Maria's relationship floor.
- Contrasting provider: protected; valid active provider profile and community memberships.
- Separate steward/admin personas: never used for public demo validation.
- Additional ordinary members: shared neighbors, one-sided neighbors, bridges, isolates, requesters,
  helpers, providers, and at least one inaccessible outsider.
- Ambient actors: clearly tagged by fixture classification and eligible for simulation.

No password or secret is committed in the manifest. Credential material comes from the environment;
the manifest carries identities and roles only.

### Communities and topology

- Six communities cover mutual-aid/neighborhood, sharing, professional/provider, and group behavior,
  including a sister-community relationship and a cross-community path.
- Every aggregate-validation community has at least five distinct active members, satisfying the
  ADR-082 privacy cohort floor.
- Topology includes redundant triangles, a bridge person, sparse edges, and isolates.
- Maria's ordinary story has a path degree of at most two, at least three shared named people, and at
  least four visible one-hop people on each side.
- The provider story gives a truthful lower-overlap contrast; no edges are invented merely to make
  the visual attractive.
- Platform-wide completed-help topology remains separate from request reachability and community-
  scoped relationship strength, per ADR-077/078.

### Requests, exchanges, and providers

- Valid examples of all built-in request types and payload vocabularies.
- Community-, trust-network-, sister-community-, and platform-reachable requests, plus an
  intentionally unreachable outsider case.
- Open, proposed, matched, completed, rejected/declined, cancelled, expired, and forgotten lifecycle
  states with internally coherent children.
- Prior similar and unrelated completed exchanges that exercise server-owned dibs reasoning.
- Provider profile, rate/service data, community affiliation, pending provider offer, and public
  provider-rating exception without exposing ordinary-member reputation.
- Recent completed exchanges/new memberships for seven-day community pulse and older history for
  self reputation, trust, and memory surfaces.

### Age bands

Manifest ages are chosen around actual platform windows, including 7/14-day activity, 30-day trust
half-life and expired-unmatched retention, 60-day request TTL, 6-month karma half-life, and 180-day
completed-content/message retention. Already-forgotten rows carry the canonical sentinels and
timestamps; the seed never creates an overdue but internally unprocessed row and calls it healthy.

Durable Maria edges use truthful repeated exchanges and resulting stability rather than demo-only
decay exemptions. Nearly-forgotten examples are not dependencies of the guided story.

## Data Model

No production schema migration is planned. The fixture manifest is an operational development model,
not a new source of application truth.

Conceptual manifest shape:

```ts
interface DemoFixtureManifest {
  version: 1;
  tuning: {
    peopleTarget: number;
    minimumStoryRunwayDays: number;
    richFloor: {
      maxPathDegree: number;
      minSharedPeople: number;
      minOneHopPerSide: number;
    };
  };
  people: FixturePerson[];
  communities: FixtureCommunity[];
  memberships: FixtureMembership[];
  requests: HistoricalRequestFixture[];
  exchanges: HistoricalExchangeFixture[];
  providers: ProviderFixture[];
  governance: GovernanceFixture[];
  activities: ActivityFixture[];
  expectedBehaviors: FixtureExpectation[];
}
```

The compiler resolves semantic references, derives stable UUIDs, converts age offsets using the reset
anchor, orders inserts by dependency, and rejects:

- dangling or duplicate keys;
- impossible request/match/offer state combinations;
- Maria with an admin/moderator role or no active membership;
- a protected person admitted to the ambient simulator pool;
- privacy cohort fixtures below five people;
- story topology below its hard floor;
- derived numeric reputation assertions in place of intended behaviors.

Completed exchanges and feedback are then replayed through application-owned projection functions to
rebuild connections, community trust edges, relationship stability/last-interaction time, and
reputation aggregates. Those functions accept the source event time explicitly. The manifest never
contains arbitrary trust-edge weights or private reputation scores.

The manifest may be tuned after live observation, but its schema version and expectation set make
changes reviewable rather than becoming an opaque SQL dump.

## API Endpoints

No new public application endpoint is required. The reset and verifier use existing ordinary routes.

| Method | Path | Fixture use | Auth/expectation |
|---|---|---|---|
| POST | `/auth/login` | Obtain ordinary validation personas | Synthetic credentials from environment |
| POST | `/auth/demo-session` | Final guided-session coherence | Enabled only after verified IDs; Maria read-only |
| GET | `/requests/curated` and feed routes | Reachability/ranking/lifecycle texture | Ordinary member; no cross-user metrics |
| POST | `/requests` | Create replacement Maria stories | Ordinary Maria token, never demo-read-only token |
| POST | `/matches` | Create ordinary helper decision | Selected helper's ordinary token |
| POST | `/providers/offers` | Create provider decision | Selected provider's ordinary token |
| GET | request/match/offer relationship-context routes | Reciprocal story validation | Only request-authorized participants |
| GET | `/trust/graph*`, `/trust/neighborhood/:userId` | Structural/topology fixtures | Existing privacy scope and caps |
| GET | `/reputation/me/community-summary` | Maria self-facing age/reputation state | Self only |
| GET | aggregate/provider routes | Cohort and provider exceptions | Existing ADR-082 classes |
| GET | `/requests/retention-policy` | Retention transparency fixture | Active member |
| GET | community pulse/governance routes | Recent activity and qualitative governance | Active member; no member metrics |

The operational tool may use direct database access for backup, truncate, historical timestamp load,
and narrow referential sanity checks. It may not substitute direct SQL reads for the outward
acceptance contract.

## Verified Maria Story IDs

The historical manifest creates the relationship preconditions; it does not hard-code live story IDs.
The story publisher:

1. authenticates Maria, the selected helper, and selected provider as ordinary accounts;
2. creates the ordinary and service requests through `POST /requests`;
3. creates a proposed ordinary match and pending provider offer through their ordinary APIs;
4. re-reads authoritative request, match, offer, and relationship-context state;
5. rejects any closed, expired, incoherent, sparse, or unauthorized story;
6. emits the persona email plus four server-generated IDs only after every validation passes.

On the demo server, an explicit configuration-write option atomically replaces only the five known
demo variables in `.env.demo`, preserves a backup, restarts the affected service, and then validates
`POST /auth/demo-session` again. Partial output is never treated as ready configuration.

## Fixture Health and Story Rotation

The read-only health command checks the critical story and privacy contract daily and exits non-zero
when the demo is no longer safe/ready. It reports the minimum request-expiry runway and warns before
the configured floor (initially 14 days).

Story rotation is a separate explicit `--apply` operation. It creates and verifies replacement live
stories, atomically switches configuration, revalidates the public demo session, then retires the old
stories. It does not reset historical data, does not run automatically, and does not mutate on a
failed verification. Full reset remains a deliberate maintenance operation.

Time continues to affect every fixture. Aging examples may cross their intended boundaries; health
reports that drift. No fixture receives immortality, a frozen clock, or a demo-only retention/decay
exception.

## Validation Contract

### Reset readiness

- Correct demo database fingerprint; advisory lock acquired; backup restorable.
- Every managed table classified; dry-run and apply deletion/seed counts reconcile.
- Second reset from the same manifest reproduces stable historical IDs and relative state.
- Simulator and cleanup are paused during mutation; protected-core exclusion is proven before resume.

### Privacy-scoped API readiness

- Maria is synthetic, active, non-admin, and owns both live requests.
- Ordinary request is open with the selected helper's proposed match.
- Provider request is open with the selected provider's pending offer.
- The same named topology/path is disclosed under reciprocal orientation, with only role/orientation
  copy changing.
- Ordinary story clears the rich floor; provider story supplies truthful contrast.
- An unrelated member cannot retrieve request-bound relationship context.
- Cross-user exact reputation, karma, weights, counts, history text, and sensitive timestamps are
  absent; self/provider/community-aggregate exceptions behave exactly as ADR-082 permits.
- Demo-session mutations return 403; ordinary authorized operations remain functional.
- Graph, feed, pulse, retention, dibs, provider, self-reputation, governance, and activity fixtures
  produce their declared outward states.
- Both live requests retain at least the configured expiry runway.

### Human validation

- API smoke: run the machine-readable verification report against the deployed environment.
- Database sanity: compare classified table counts, foreign-key integrity, reset anchor, and backup.
- UI: complete the guided Maria demo and inspect Home, Community, Network, Profile/Memory, Providers,
  and retention transparency on desktop and mobile.
- Within five seconds a viewer can explain how Maria and the helper connect, where each belongs, and
  which offerer acts as a provider.

## Error Handling and Recovery

- Unknown environment, schema drift, backup failure, lock contention, compiler failure, or service
  unavailability aborts before destructive work whenever possible.
- Historical seed failure rolls back its transaction.
- Post-seed/story/API validation failure leaves demo entry disabled and mutation jobs paused or in a
  clearly reported state; it never publishes IDs from a partial run.
- The tool logs semantic keys and safe counts, not passwords, tokens, database URLs, or secrets.
- Recovery offers two bounded choices: rerun the idempotent baseline from the manifest or restore the
  captured backup. Public enablement is always a final explicit step.

## Testing Strategy

1. **Compiler unit tests (TDD first)**: semantic references, UUID derivation, relative ages, lifecycle
   validation, role/simulator constraints, deterministic output, and tuning bounds.
2. **Preflight/reset tests**: demo fingerprint, default dry-run, `--apply`, advisory lock, table
   classification drift, backup requirement, transaction rollback, and safe rerun.
3. **Database integration tests**: apply to an ephemeral migrated PostgreSQL database twice; assert
   referential integrity, stable historical IDs, regenerated anchor-relative times, and current table
   coverage.
4. **Age/cleanup tests**: expiry, retention sentinels, karma/trust decay bands, pulse windows, and no
   guided-story dependency on volatile near-threshold rows.
5. **API/privacy tests**: ordinary/self/provider/aggregate classes, reciprocal topology, inaccessible
   context denial, server-generated story readback, and demo-write rejection.
6. **Operations tests**: health is read-only; rotation fails closed; env replacement is allowlisted,
   atomic, and backed up; simulator excludes every protected person.
7. **Staged rehearsal**: execute one approved full reset during planned downtime, run API + DB + UI
   validation, resume ambient simulation, and prove a follow-up health check remains green.

Passing TDD tests are promoted to regression. Unit + regression remain blocking; the full staged reset
requires explicit Admin authorization because it destroys deployed demo data.

## Critical Implementation Notes

1. **PostgreSQL, not the legacy truncate list, defines the reset surface.** Classify every table in
   managed application schemas and fail closed on additions; preserve migrations/schema/catalogs only.
2. **Dry-run is the default; destructive work requires `--apply`, a demo fingerprint, an advisory
   lock, paused mutation jobs, and a completed restorable backup.** Planned downtime does not relax
   these controls.
3. **One reset anchor drives every relative age.** Never use fixed calendar dates or freeze the clock.
4. **Maria is the dedicated public persona and is non-admin by construction.** Validate live
   memberships; do not trust stale JWT role claims or manifest intent alone.
5. **Protected-core people never enter the simulator actor pool.** Exclusion must cover Maria, helper,
   provider, shared neighbors, and every story dependency—not only `DEMO_PERSONA_EMAIL`.
6. **Historical source state may be loaded directly where APIs cannot express time, but outward APIs
   are the completion authority.** Direct row checks are sanity checks, never product validation.
7. **Do not hand-author derived scores as the story.** Seed canonical exchanges/feedback inputs,
   rebuild projections through application-owned domain functions using source event time, and assert
   qualitative outward behavior; exact private metrics stay out of ordinary validation.
8. **Respect platform time semantics.** Build fresh, pulse, decay, retention, and forgotten lanes from
   the implemented 7/14/30/60/180-day and six-month rules; overdue rows must already reflect cleanup.
9. **Durable Maria topology comes from truthful repeated completed exchanges and stability.** No direct
   trust-edge invention, immortality, or demo-only decay threshold.
10. **Trust topology is platform-wide; strength and membership remain scoped.** Request visibility is
    independent and must cover community, trust-network, sister, platform, and denial cases.
11. **The Maria ordinary story must retain the Sprint 116 rich floor:** ≤2-degree path, ≥3 shared
    people, and ≥4 visible one-hop people per side. Provider contrast must remain truthful.
12. **Live story IDs are server-generated and configuration is published only after authoritative
    re-read.** Never trust mutation response shape, partial output, or terminal story rows.
13. **Reciprocal and privacy validation are mandatory.** Reverse participant orientation, test an
    unrelated member denial, scan protected responses for forbidden metrics, and prove demo writes 403.
14. **Health is read-only and rotation is explicit.** Neither may silently repair topology, touch the
    baseline, or trigger a full reset.
15. **Fixture tuning is expected but governed.** Put density/age/texture knobs in the typed manifest;
    hard privacy, lifecycle, cohort, simulator, and relationship floors are not tunable away.
16. **Resume in dependency order:** validated baseline → live stories → demo configuration → public
    demo → cleanup → ambient simulation. Any failure leaves the demo disabled with a bounded recovery.
17. **Update existing reset/rehearsal/docs paths instead of creating parallel v2 scripts.** Fix forward
    so there is one supported operator workflow.
